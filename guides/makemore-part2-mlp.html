Part 0 · 0:00 – 9:00

The problem, and the paper we copy

Why counting stops working, and the 2003 paper whose design we are about to build.

1

Why a bigram is not enough

▶ 0:00

Last video the model looked at one previous letter. Its names did not sound much like names.

  • That model was a table of counts: one row for each possible previous letter.
  • To use more context, the table needs one row for every possible context.
  • 2 letters of context: 27 × 27 = 729 rows. 3 letters: about 20,000 rows.
  • Most rows would get very few counts. In his words, the whole thing "explodes and doesn't work very well".
So what now?
Today we use a multi-layer perceptron (MLP), a small neural network, to predict the next character.
In one lineMore context makes a counting table explode, so we switch to a neural network.
2

The plan: copy Bengio et al. 2003

▶ 2:00

We follow one paper: “A Neural Probabilistic Language Model” by Bengio, Ducharme, Vincent and Jauvin (2003).

  • It is not the first paper to predict the next word with a neural net, but it was very influential and is nicely written.
  • The paper has 19 pages. He invites you to read it; it is "very readable".
  • The paper works on words (a vocabulary of 17,000). We work on characters (27). The modelling idea is the same.
  • Same recipe as before: the net outputs a probability for every next token, and we maximise the likelihood of the training data.
In one lineWe copy the paper's design, with 27 characters instead of 17,000 words.
3

Embeddings: every token becomes a point

▶ 3:01

The paper gives each of its 17,000 words a list of numbers, say 30. This list is called an embedding (a feature vector).

  • So there are 17,000 points in a 30-dimensional space. "That's a lot of points for a very small space."
  • At the start the points are placed at random.
  • During training, backpropagation moves them. Words with similar meanings drift to nearby places; unrelated words end up elsewhere.
In one lineAn embedding is a learnable list of numbers per token; training moves similar tokens close together.
4

Why embeddings help you generalise

▶ 4:01

Say the model must finish “A dog was running in a ___”, but that exact phrase never appeared in the training data.

  • With plain counts you have no clue what comes next. He calls this being out of distribution.
  • With embeddings you can still do well. Maybe the training data had “The dog was running in a room”.
  • If the net learned that a and the are interchangeable, it can put their embeddings close together. Then what it knows about one carries over to the other.
  • Same for cats and dogs (both animals, similar contexts) and for walking and running.
The cat is walking in the bedroomA dog was running in a roomThe cat is running in a roomA dog is walking in a bedroomThe dog was walking in the room

The sentences are the paper's own examples. Knowledge is "transferred through the embedding space".

In one lineSimilar tokens get similar embeddings, so knowledge about one sentence carries over to similar ones.
5

The network in the paper

▶ 5:50
  1. Each of the 3 previous words is an index (a number from 0 to 16,999).
  2. Each index picks a row of the matrix C (17,000 × 30). That row is the word's 30 numbers. All three positions share the same C.
  3. The three rows go side by side: 90 numbers in total.
  4. Hidden layer: fully connected to those 90 numbers, then tanh. Its size is a hyperparameter, for example 100.
  5. Output layer: one neuron per possible next word (17,000), fully connected to the hidden layer. It is "the expensive layer".
  6. Softmax turns the 17,000 scores into probabilities. We push up the probability of the word that really came next.
Hyperparameter
A design choice that is up to you (like the hidden layer size). The network does not learn it.

Learned by backpropagation: C, the hidden weights and biases, and the output weights and biases.

In one lineEmbedding lookup, glue, tanh hidden layer, big output layer, softmax: everything is learned together.

Build the dataset with a rolling window

▶ 9:40

block_size is the context length: how many characters we use to predict the next one. Here it is 3, as in the paper.

block_size = 3
X, Y = [], []                          # inputs, and the labels for them
for w in words[:5]:                    # only 5 names while we develop
    context = [0] * block_size         # start with '...'
    for ch in w + '.':
        ix = stoi[ch]
        X.append(context)
        Y.append(ix)
        context = context[1:] + [ix]   # crop the oldest, append the newest

X = torch.tensor(X)                    # (32, 3)
Y = torch.tensor(Y)                    # (32,)
  • Five names give 32 examples. X is (32, 3) and Y is (32), both integers.
  • He briefly tries block sizes 4, 5 and 10 (10 letters to predict the 11th), then goes back to 3.
  • Later he removes the [:5] so the whole dataset is used.
In one lineEvery name becomes many rows of (context of 3 letters → next letter) by sliding a window.

The embedding table C

▶ 12:00

We have 27 characters. Give each one an embedding. We start tiny, with 2 numbers per character (the paper squeezes 17,000 words into about 30).

C = torch.randn((27, 2))      # 27 rows (characters), 2 columns (embedding numbers)

  • The numbers are random for now. Training will tune them.
  • Two dimensions is small on purpose: we can draw them later.
In one lineC is a 27 × 2 table: row i holds the two learnable numbers for character i.

Embed one letter: index or one-hot?

▶ 13:00

Two ways to get the embedding of the integer 5. They give the same answer.

C[5]                                                      # tensor([0.1615, 1.3169])
F.one_hot(torch.tensor(5), num_classes=27).float() @ C    # same two numbers
Two errors he hits on purpose

one_hot needs a tensor, not a plain int.

It returns integers (long), but C is float, so the multiply fails: “expected scalar type Long but found Float”. Fix: .float().

  • So an embedding is secretly a first layer: no tanh, weight matrix C, fed with one-hot inputs.
  • We just index, because it is much faster, and forget the one-hot view.
In one lineC[5] equals one_hot(5) @ C, so an embedding is a first linear layer written as a lookup.

▶ 16:30

PyTorch indexing is flexible. You can index with a list, a tensor, repeated numbers, even a 2D tensor.

The hidden layer, and a shape problem

▶ 18:30

Hidden layer weights W1 and bias b1. Inputs per example: 3 letters × 2 numbers = 6. How many neurons? Our choice: 100.

W1 = torch.randn((6, 100))
b1 = torch.randn(100)

emb @ W1 + b1
# RuntimeError: mat1 and mat2 shapes cannot be multiplied (96x2 and 6x100)
Why it fails
emb is (32, 3, 2) (the three embeddings are stacked), but the layer needs (32, 6): the three embeddings side by side.

He shows three ways to do the gluing: "there are usually many ways of implementing what you'd like to do in torch". Some are faster, better or shorter.

In one lineemb is (32, 3, 2) but the layer needs (32, 6): the three embeddings must be glued side by side.
12

Way 1: torch.cat

▶ 20:00

torch.cat joins a list of tensors along one dimension.

torch.cat([emb[:, 0, :], emb[:, 1, :], emb[:, 2, :]], 1).shape    # (32, 6)
  • emb[:, 0, :] is the first letter's embedding for all examples: (32, 2). Same for 1 and 2.
  • Join along dimension 1 (side by side), not 0 (which would stack them taller).
  • It works, but it is "kind of ugly": we typed the number 3 into the code, so a different block size breaks it.
In one linecat along dimension 1 glues pieces side by side, but this version only works for block size 3.

Way 2: torch.unbind

▶ 22:00
torch.cat(torch.unbind(emb, 1), 1).shape    # (32, 6)
  • unbind removes one dimension and returns a tuple of all the slices along it. Here: three tensors of (32, 2).
  • That is exactly the list we typed by hand. Now it works for any block size: 3, 5, 10.
  • But there is a much better way (next card).
In one lineunbind splits a dimension into a list, so cat(unbind(emb, 1), 1) works for any block size.

Way 3: view, the free reshape

▶ 23:30
a = torch.arange(18)      # shape (18,)
a.view(2, 9)              # 2 rows of 9
a.view(9, 2)              # 9 rows of 2
a.view(3, 3, 2)           # 3 blocks of 3 rows of 2

  • He checks it: emb.view(32, 6) == torch.cat(torch.unbind(emb, 1), 1) is True everywhere.

15

Why view is free

▶ 24:40

Every tensor keeps its numbers in storage: always one flat, one-dimensional row in memory.

  • a.storage() prints 0 to 17 in order, whatever shape a has.
  • .view(...) only changes some attributes that say how to read that row: the storage offset, the strides and the shape.
  • So nothing is changed, copied, moved or created. It is "extremely efficient".
  • torch.cat cannot do that. It creates a new tensor with new memory.

He recommends Eric's blog post “PyTorch Internals” and says he may make a video on it.

In one lineview is nearly free because only metadata changes, while cat copies the data into new memory.

The hidden activations

▶ 27:00
h = torch.tanh(emb.view(-1, 6) @ W1 + b1)     # (32, 100)
  • Don't type the 32. Use emb.shape[0] or -1: PyTorch works out the missing number so the element count matches.
  • tanh squeezes every value into the range -1 to 1.
  • h holds the hidden activations: 100 numbers for each of the 32 examples.
Where we are
Input (32, 3) → embed (32, 3, 2) → reshape (32, 6) → hidden (32, 100).
In one lineh = tanh(emb.view(-1, 6) @ W1 + b1) gives 100 numbers in [-1, 1] for each example.

Check the bias broadcast

▶ 28:15

One thing he had glossed over: the + b1. Does broadcasting do what we want?

  • (32, 100) plus (100): shapes line up from the right. PyTorch adds a fake dimension to b1, so it is (1, 100), then copies it down over the 32 rows.
  • So the same bias row goes to every example. That is correct.
  • "It's always good practice to just make sure, so you don't shoot yourself in the foot."
In one lineBroadcasting adds the same b1 to every example, which is what we want.

Softmax by hand

▶ 29:50

Exactly as in the last video: make the scores positive with exp, then divide each row by its total.

counts = logits.exp()
prob = counts / counts.sum(1, keepdims=True)     # (32, 27)
prob[0].sum()                                    # 1.0  (every row sums to one)
  • keepdims=True keeps the row sums as a column (32, 1), so each row is divided by its own total.
In one lineexp, then divide by the row sum, turns logits into probabilities.
20

The loss: pluck the right probability

▶ 30:30

For each example we want the probability the net gave to the true next character (from Y).

prob[torch.arange(32), Y]                        # one probability per example
loss = -prob[torch.arange(32), Y].log().mean()   # tensor(17.2955)
  • torch.arange(32) walks down the rows. Y says which column to take in each row.
  • Some values are about 0.2. Many are tiny, like 0.0000001: the net thinks the true answer is very unlikely. It is untrained, so that is no surprise.
  • Ideally every number is 1. The loss starts around 17 and we want it down.
My note
Guessing uniformly over 27 letters would score about ln 27 ≈ 3.3. A loss of 17 is far worse than guessing: the random weights are confidently wrong.
In one lineThe loss is the average negative log of the probability given to the true next letter; untrained it is about 17.

Tidy up: one parameters list, a seed

▶ 32:20
g = torch.Generator().manual_seed(2147483647)    # for reproducibility
C  = torch.randn((27, 2),   generator=g)
W1 = torch.randn((6, 100),  generator=g)
b1 = torch.randn(100,       generator=g)
W2 = torch.randn((100, 27), generator=g)
b2 = torch.randn(27,        generator=g)
parameters = [C, W1, b1, W2, b2]

sum(p.nelement() for p in parameters)            # 3481
  • A seeded generator makes the random start repeatable.
  • All learnable tensors go into one list, so counting and updating them is easy.
  • The whole forward pass is now six lines. With these seeded weights the starting loss is 17.77.
In one lineAll learnable tensors live in one list, parameters: 3,481 numbers to learn.
22

Use F.cross_entropy instead

▶ 33:00
loss = F.cross_entropy(logits, Y)       # tensor(17.7697), the same number

This one call replaces the three lines (exp, normalise, pluck and average the log). He wrote them by hand "for educational reasons", but "you'd never use this in practice". Why:

  1. Faster. PyTorch does not create all the in-between tensors. It uses fused kernels: many steps in one.
  2. Simpler backward pass. Like tanh in micrograd, where the derivative is just 1 − t², the whole expression has a much simpler derivative than its parts.
  3. Safer numbers. The next two cards.
In one lineF.cross_entropy(logits, Y) gives the same loss, but faster, simpler to differentiate and safer.
23

Danger: exp can overflow

▶ 35:00

See what happens to the probabilities for different logits (4 numbers instead of 27, to keep it small):

logitsresult
[-2, -3, 0, 5][0.0009, 0.0003, 0.0067, 0.9921] fine
[-100, -3, 0, 5]still fine: exp(-100) is just a tiny number near 0
[-100, -3, 0, 100][0, 0, 0, nan] broken
  • Very negative logits are harmless. Very positive ones are not: exp(100) is inf, because the float runs out of range.
  • inf divided by inf gives nan.
  • Logits can grow large during optimisation, so this really can happen.
In one lineVery large positive logits make exp overflow to inf, and the probabilities turn into nan.
24

The fix: subtract the biggest logit

▶ 36:40

Adding or subtracting the same number from every logit changes nothing: the probabilities come out identical.

softmax(x − c) = softmax(x)
  • PyTorch finds the largest logit and subtracts it first. The biggest becomes 0 and the others become negative.
  • Negative numbers are safe for exp, so it can never overflow.
logits = torch.tensor([-5, -3, 0, 5]) - 5      # shifted by the max
probs  = logits.exp() / logits.exp().sum()     # [4.5e-05, 3.3e-04, 6.7e-03, 0.993]

Even the broken case works once you subtract 100. F.softmax, used when sampling later, has the same protection.

That makes three reasons to call cross_entropy: a faster forward pass, a faster backward pass, and numbers that stay well-behaved.

In one lineSubtracting the biggest logit before exp changes nothing mathematically and prevents overflow.

▶ 38:00

Try to answer out loud first, then open each one.

What is block_size, and what shapes do X and Y have for five names?
block_size is how many previous characters predict the next one (3 here). Five names give 32 examples, so X is (32, 3) and Y is (32), both integers.
Why does C[5] give the same result as one_hot(5) @ C?
The one-hot vector has a single 1, so the multiplication keeps only row 5 of C and zeros out everything else. Indexing is the faster way to do the same thing.

emb is (32, 3, 2) but W1 needs (32, 6). The best fix is emb.view(-1, 6), which is free because it only changes how the same storage is read. cat and unbind also work but copy memory.
How many parameters does the 100-neuron network have?
27×2 (C) + 6×100 + 100 (W1, b1) + 100×27 + 27 (W2, b2) = 54 + 700 + 2,727 = 3,481.
Why does adding b1 of shape (100) to a (32, 100) tensor work?
Broadcasting lines shapes up from the right, treats b1 as (1, 100) and copies it down every row. Each example gets the same bias.
What loss does the untrained net start at, and what does that tell you?
About 17. Uniform guessing would be about 3.3, so the random weights are confidently wrong.

Make the loss go down

The training loop, mini-batches, and a sensible way to choose the learning rate.

The training loop

▶ 38:02
for p in parameters:
    p.requires_grad = True

for _ in range(1000):
    # forward pass
    emb = C[X]                                    # (32, 3, 2)
    h = torch.tanh(emb.view(-1, 6) @ W1 + b1)     # (32, 100)
    logits = h @ W2 + b2                          # (32, 27)
    loss = F.cross_entropy(logits, Y)
    # backward pass
    for p in parameters:
        p.grad = None
    loss.backward()
    # update
    for p in parameters:
        p.data += -0.1 * p.grad

print(loss.item())
  1. Forward pass to get the loss.
  2. Reset gradients. p.grad = None is the same as zero in PyTorch.
  3. loss.backward() fills every parameter's gradient.
  4. Update: nudge each parameter a little against its gradient. Here the step size is 0.1.
Don't forget
requires_grad = True on every parameter first. Without it, backward() has nothing to fill.
In one lineEach step: forward, clear gradients, backward, then move every parameter against its gradient.

Mini-batches

▶ 42:30

In practice people update on a small random piece of the data each step: a mini-batch.

ix = torch.randint(0, X.shape[0], (32,))     # 32 random row numbers
emb = C[X[ix]]                               # (32, 3, 2)
h = torch.tanh(emb.view(-1, 6) @ W1 + b1)
logits = h @ W2 + b2
loss = F.cross_entropy(logits, Y[ix])        # the same ix picks the labels
  • Each step is now "almost instant".
  • The gradient from 32 examples is only an estimate, but it points the right way. His words: "it's much better to have an approximate gradient and take more steps than to evaluate the exact gradient and take fewer steps."
  • The printed loss is for that mini-batch only, so it is noisy. To see the real picture, compute the loss on all of X and Y now and then. After 1,000 steps it is about 2.6.
Use the same ix
The labels must be picked with the same random numbers as the inputs: X[ix] and Y[ix].
In one lineTrain on random mini-batches: a rough gradient taken many times beats an exact one taken rarely.

Is 0.1 the right step size? Bracket it

▶ 45:30

So far 0.1 was a guess. Here is a way to find a good learning rate. First, find a rate that is clearly too slow and one that is clearly too wild.

Reset the weights, run about 100 steps with a rate, and watch the loss:

learning ratewhat he saw
very smallloss barely moves: too low

Sweep the learning rate

▶ 47:00

Instead of guessing, try 1,000 rates from 0.001 to 1, one per step, and record the loss each time.

lre = torch.linspace(-3, 0, 1000)     # 1000 exponents from -3 to 0
lrs = 10**lre                         # 0.001 ... 1

lri, lossi = [], []
for i in range(1000):
    ...                               # forward and backward as before
    lr = lrs[i]                       # a larger rate every step
    for p in parameters:
        p.data += -lr * p.grad
    lri.append(lre[i])                # keep the exponent for the x-axis
    lossi.append(loss.item())
  • Stepping evenly between the exponents -3 and 0 spaces the rates exponentially: many small ones, fewer big ones. Linear spacing would waste almost all the steps on large rates.
  • Start from fresh random weights, then plot lri against lossi.
In one lineRaise the learning rate a little each step, on a log scale, and record the loss at each one.

▶ 53:00

What are the four steps of one training iteration?

Why did the loss on 32 examples fall to about 0.25 but not to 0?

It spaces the rates exponentially, so each size of rate (0.001, 0.01, 0.1, 1) gets a fair share of steps.
What is learning rate decay?
Dividing the rate by about 10 late in training, to take smaller steps while the loss levels out.
In one lineIf you can answer these, training is done.

Splits, scaling up, and the final score

Why training loss isn't enough, how to split the data, and how the model improves.

34

Lower loss is not the whole story

▶ 53:20

Our net is still small. But nets can grow: 10,000, 100,000, millions of parameters.

  • The more capacity, the better a net can overfit: the training loss can fall to almost zero.
  • But then the net is just memorising the training set word for word.
  • If you sample from it, you get exactly the training names, nothing new.
  • If you measure the loss on names it has not seen, it can be very high. It is not a good model.

So we need a fair test: data the net never trained on.

In one lineA model can drive the training loss to zero by memorising, so training loss alone can't tell you if it is good.
35

Three splits: train, dev, test

▶ 54:30
  • Train (about 80%): used to fit the parameters, by gradient descent as we do.
  • Dev or validation (about 10%): used to choose the hyperparameters. Examples: the hidden layer size, the embedding size, the strength of regularisation (not used yet). Try many settings, keep the best on dev.
  • Test (about 10%): the final score. Look at it very sparingly.
Why test is special
Each time you look at the test loss and learn something from it, you are training on the test set a little. Look too often and you overfit it too.
In one lineTrain fits the weights, dev picks the settings, test gives the honest final score, and you rarely peek at it.

Train ≈ dev means underfitting

▶ 60:00

He also computes the loss on the whole training split. It is about the same as the dev loss.

  • That means the net is not overfitting. It is not even powerful enough to memorise the data.
  • This is called underfitting. "Our network is very tiny, very small."
  • The fix he expects to help: make the network bigger.
Rule of thumb
Train loss ≈ dev loss: the model is too small. When the dev loss pulls above the train loss (you will see this near the end), it has started to overfit.
In one lineWhen train and dev loss are about equal, the model is underfitting: it is too small.

Maybe the embedding is the bottleneck

▶ 64:20

A much bigger hidden layer did not help as much as expected. He lists some suspects:

  • The embedding is too small. We squeeze 27 characters into just 2 numbers each, and the net may not be able to use that space well. This is his main guess.
  • The batch is too small. Too much noise in the gradient, so the weights "thrash". A bigger batch gives a more accurate gradient.
  • The learning rate. Just lowering it already made "quite a bit of progress".

Before changing the embedding size he wants to look at it, because with more than 2 numbers it can't be drawn.

Tuning by hand is shaky

▶ 69:00

He admits that all this was done "haphazardly".

  • He has no confidence that the learning rate, or the moment he lowers it, is set well: "we just do it at random". "The optimisation here is kind of suspect."
  • In practice: turn every setting into a hyperparameter, run lots of experiments, and keep whichever gives the best dev loss.
  • Only then take that one model and evaluate on test, a single time. That is the number you report "in your paper or wherever".
  • Train loss (2.17) and dev loss (2.2) are starting to drift apart, a first hint of overfitting.

Ways forward he lists: tune the optimisation, change the sizes, or feed in more than 3 characters of context.

Gotchas he points out

▶ 13:00
  1. one_hot needs a tensor, and returns integers: cast with .float() before multiplying.
  2. Don't hard-code the batch size. Use -1 or emb.shape[0] in view.
  3. Don't hard-code magic numbers. The 6 in view(-1, 6) must become 30 when the embedding grows.
  4. Check broadcasting. (32, 100) + (100) is fine, but always verify.
  5. view is free, cat is not. cat creates new memory.
  6. requires_grad = True on every parameter, and p.grad = None before each backward.
  7. Use the same ix for X[ix] and Y[ix].
  8. Mini-batch loss is noisy. Evaluate on the whole split to know where you are.
  9. Large positive logits overflow exp. Use F.cross_entropy / F.softmax.
  10. Find the learning rate by sweeping it, don't guess.
  11. Low training loss can be memorising. Judge by the dev loss.
  12. Peek at the test set rarely.
In one lineMost traps are about shapes, copies, and judging the model on the wrong data.

The whole recipe in one block

▶ 38:02

Everything from the video, in order, as it ended up (settings as he describes them).

# 1. data: 80 / 10 / 10 split of the shuffled names, block_size = 3
Xtr, Ytr   = build_dataset(words[:n1])
Xdev, Ydev = build_dataset(words[n1:n2])
Xte, Yte   = build_dataset(words[n2:])

# 2. parameters
g  = torch.Generator().manual_seed(2147483647)
C  = torch.randn((27, 10),  generator=g)
W1 = torch.randn((30, 200), generator=g)
b1 = torch.randn(200,       generator=g)
W2 = torch.randn((200, 27), generator=g)
b2 = torch.randn(27,        generator=g)
parameters = [C, W1, b1, W2, b2]
for p in parameters:
    p.requires_grad = True

# 3. train on random mini-batches of the train split
for i in range(200000):
    ix = torch.randint(0, Xtr.shape[0], (32,))
    emb = C[Xtr[ix]]                                # (32, 3, 10)
    h = torch.tanh(emb.view(-1, 30) @ W1 + b1)      # (32, 200)
    logits = h @ W2 + b2                            # (32, 27)
    loss = F.cross_entropy(logits, Ytr[ix])
    for p in parameters:
        p.grad = None
    loss.backward()
    lr = 0.1 if i < 100000 else 0.01                # decay for the second half
    for p in parameters:
        p.data += -lr * p.grad

# 4. score on dev (about 2.17), and only at the very end, on test
emb = C[Xdev]
h = torch.tanh(emb.view(-1, 30) @ W1 + b1)
loss = F.cross_entropy(h @ W2 + b2, Ydev)
In one lineSplit, build parameters, mini-batch loop, decay the rate, score on dev.
