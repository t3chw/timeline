Why look inside the network?

The goal of this lecture, and the code we start from.

1

Why look inside the network?

▶ 0:00

Last time we built an MLP. Next we want bigger networks: RNNs, GRUs, LSTMs. First, one lecture to understand what happens inside a network while it trains.

  • We want a good feel for the activations (the numbers each layer produces) and the gradients flowing backwards, and how they behave.
  • This explains the history of the architectures. An RNN is very expressive, in principle able to implement any algorithm, but it is hard to optimise with ordinary gradient descent.
  • The key to why is how activations and gradients behave during training. Many later variants were invented to improve exactly that.
In one lineBefore bigger networks, learn to read activations and gradients, because that is why RNNs were hard to train.

The starting code, tidied up

▶ 1:01

Same MLP as last time, with the magic numbers pulled out into variables.

n_embd = 10         # size of each character's embedding
n_hidden = 200      # neurons in the hidden layer

3

torch.no_grad

▶ 3:10

Anything run under @torch.no_grad() is assumed never to need gradients.

  • PyTorch then skips all the bookkeeping it normally does for a later backward(). It is as if every tensor had requires_grad=False.
  • That makes evaluation more efficient: no graph is kept in memory.
  • You can also use it as a context manager: with torch.no_grad(): .... We will use that again for batch norm.
  • Sampling works as before. The names are nicer than the bigram's, "still not fully name-like", but this is our starting point.
In one lineno_grad tells PyTorch you will not call backward, so it skips building the gradient graph.

The loss should not start at 27

The first thing wrong with the initialisation, and how to see it with one number.

4

The first problem: loss 27 at step 0

▶ 4:30

Look at the very first printed loss. At step 0 it is 27.88, and within a few iterations it falls to about 1 or 2.

      0/ 200000: 27.8817
  • That rapid drop means the initialisation is badly set. There are several things wrong, and this is the first.
  • In neural net training you almost always have a rough idea what loss to expect at the start. It depends on the loss function and the problem. 27 is not what we expect.
In one lineA starting loss far above what you expect tells you the initialisation is wrong.
5

What loss should we expect?

▶ 5:00

There are 27 characters that could come next. At the start we have no reason to prefer any, so the net should output a uniform distribution: each character gets probability 1/27.

-torch.tensor(1/27.0).log()      # tensor(3.2958)
  • The loss is the negative log of the probability given to the right answer, so the expected starting loss is about 3.30.
  • We got 27.88 instead: much, much higher.
My note
27.88 ÷ 3.30 is about 8.4, so the net starts roughly eight times worse than random guessing.
In one lineWith 27 equally likely characters the expected starting loss is -ln(1/27), about 3.30.
6

Confidently wrong

▶ 6:01

At the start the net makes messy probabilities: some characters it is very sure about, some not. When it is sure and wrong, the loss is huge.

logits = torch.tensor([0.0, 0.0, 0.0, 0.0])
probs = torch.softmax(logits, dim=0)       # [0.25, 0.25, 0.25, 0.25]
loss = -probs[2].log()                     # 1.3863, whatever the label is
  • With equal logits the loss is the same for every label, so there is no luck involved.
  • Random logits (torch.randn(4)) gave 2.11 in his run. Multiply them by 10 and you get extreme values and very high losses, even inf.
  • We want logits roughly zero at initialisation. They only need to be equal (all ones would also be fine), but by symmetry we choose zeros.
In one lineA net that is confidently wrong pays a huge loss; equal (near-zero) logits give the neutral loss.

Where do the big logits come from?

▶ 9:00
logits[0]
# tensor([-2.35, 36.44, -10.73, 5.72, 18.64, -11.70, ...
#          -24.45, ... 25.87, ...])

On the screen the first row of logits has values like 36 and -24. That is the fake confidence in wrong answers.

Logits are made by one line: logits = h @ W2 + b2. Two things to fix:

  1. b2 is random. We don't want to add a random bias, so start it at zero.
  2. W2 is large. Multiplying it by a small number makes the logits small.
In one lineLogits are h @ W2 + b2, so shrink W2 and zero b2 to get small logits.
8

Shrink the output layer

▶ 9:50
W2 = torch.randn((n_hidden, vocab_size), generator=g) * 0.01
b2 = torch.randn(vocab_size, generator=g) * 0
  • Scaling W2 by 0.1 gave a first loss of about 4.2. Scaling by 0.01 gave 3.32, which is the 3.30 we wanted.
  • Why not just set the weights to exactly zero? He is "very nervous" about setting a net's weights exactly to zero and promises to show why. For this one output layer he thinks it would be fine, but small random numbers are the habit.
  • He says those small numbers give "some entropy" that is used for symmetry breaking.
In one lineScale W2 by 0.01 and zero b2: the first loss drops from 27.88 to 3.32, matching the expected 3.30.
9

No more hockey stick, and a better loss

▶ 11:30

Remove the break and train for real. Two good things happen:

  • The loss curve no longer has a hockey-stick start. That shape came from the first few thousand steps just squashing down the oversized weights. We removed that "easy part", so training goes straight to the hard, useful part.
  • The final loss improves: validation 2.17 → 2.13 (train about 2.07).

The reason: we are not wasting early steps on shrinking weights, so more steps go to actually learning.

A hockey-stick loss at the start is something to look out for in any network you train.

In one lineFixing the overconfident softmax removes the hockey stick and lowers validation loss from 2.17 to 2.13.

Part 2 · 13:00 – 28:00

The hidden layer is saturated

The logits are fine now, but the hidden layer still has a deeper problem.

10

The second problem: tanh outputs are all ±1

▶ 13:00

The loss looks right, but look inside: the values of h, the hidden activations. Many of them are 1 or -1.

plt.hist(h.view(-1).tolist(), 50);        # all tanh outputs, in 50 bins
  • tanh squashes any number smoothly into the range -1 to 1.
  • The histogram has two big spikes at the ends: the tanh is "very, very active".
  • Why: the numbers going into tanh (the pre-activations) are very broad, about -5 to 15, so everything gets squashed to the ends.
In one lineIf the pre-activations are too wide, tanh pushes almost every output to -1 or +1.
11

Why a saturated tanh kills the gradient

▶ 15:00

If you know how gradients flow, this histogram makes you sweat. Recall tanh in micrograd:

def tanh(self):
    t = (math.exp(2*x) - 1) / (math.exp(2*x) + 1)
    out = Value(t, (self,), 'tanh')
    def _backward():
        self.grad += (1 - t**2) * out.grad       # chain rule
  • The incoming gradient is multiplied by 1 − t².
  • If t = ±1, the factor is 0: the gradient stops, "no matter what out.grad is".
  • If t = 0, the factor is 1: the gradient passes straight through.
  • Intuition: in a flat tail, changing the input hardly changes the output, so it has no effect on the loss. Zero gradient is the right answer.
  • The gradient through tanh can only shrink, and more the deeper you are in a tail.
In one lineA tanh in its flat tail multiplies the gradient by about zero, so the neurons below it learn nothing.
12

See it: the white map

▶ 18:30
plt.figure(figsize=(20, 10))
plt.imshow(h.abs() > 0.99, cmap='gray', interpolation='nearest')
  • It draws a Boolean table: 32 examples (rows) by 200 neurons (columns). White means the neuron is in a flat tail (more than 0.99 away from zero).
  • In his picture a lot is white: many neurons are saturated, so many gradients get destroyed.
  • The real danger is a whole white column. That is a dead neuron: no example ever lands in the active part, so it never learns.
  • He scans for white columns and finds none. So every neuron gets some gradient, and the net still trains.
In one lineA white cell is a saturated tanh; a fully white column is a dead neuron that can never learn.
13

Dead neurons and other nonlinearities

▶ 20:00

A dead neuron never activates for any input in the data, so its gradients are always zero. It is not only a tanh problem.

nonlinearityflat region?danger
tanhboth tailssaturates, gradient vanishes
sigmoidboth tailssame as tanh
ReLUeverything below 0a dead ReLU gets exactly zero gradient
leaky ReLUnonealmost always gets a gradient
ELUleft tailcan still suffer
  • A neuron can be dead from initialisation, by bad luck with its weights and bias.
  • It can also die during training. With a very high learning rate a neuron gets a huge gradient and is "knocked off the data manifold". Afterwards no example activates it, so it stays dead forever: "permanent brain damage".
  • A test: after training, push the whole training set through and look for neurons that never turn on.
In one lineNeurons can die when they sit in a flat region for every input; ReLU dies completely, leaky ReLU hardly at all.

Fix: make the pre-activations smaller

▶ 24:00

hpreact = embcat @ W1 + b1 is too far from zero. As with the logits, we want it close to zero.

W1 = torch.randn((n_embd * block_size, n_hidden), generator=g) * 0.2
b1 = torch.randn(n_hidden, generator=g) * 0.01
W2 = torch.randn((n_hidden, vocab_size), generator=g) * 0.01
b2 = torch.randn(vocab_size, generator=g) * 0
  • b1 × 0.01: tiny but not zero, "a little bit of variation and diversity" among the tanh neurons. He finds that helps optimisation a bit.
  • W1 × 0.1 first: the histogram becomes healthy and the pre-activations sit between about -1.5 and 1.5. No white cells at all.
  • He then bumps it to × 0.2 as "a nice distribution", and keeps that.
In one lineSmall W1 (×0.2) and tiny b1 (×0.01) keep tanh in its active zone with no saturated neurons.

Part 3 · 28:00 – 40:30

Where do the magic numbers come from?

A principled rule so we don't hand-tune 0.2 for every layer.

16

Hand-tuned numbers don't scale

▶ 28:00

We found 0.2 by looking at histograms. With a big net, nobody can do that by hand. There is a principled rule.

x = torch.randn(1000, 10)      # 1000 examples, 10 inputs each, std 1
w = torch.randn(10, 200)       # 200 neurons, each looking at 10 inputs
y = x @ w
x.std(), y.std()               # 0.99  ->  3.10
  • The mean stays about 0 (the operation is symmetric), but the standard deviation grows from 1 to about 3. The Gaussian expands.
  • We don't want that. We want roughly unit Gaussian activations throughout the net.
In one lineMultiplying by random weights widens the Gaussian (std 1 becomes about 3), which we don't want.
17

Divide by the square root of fan-in

▶ 30:00

fan-in = how many inputs each neuron has (here 10). The scale of the weights controls the spread of the output:

  • Weights × 5: std grows to about 15.
  • Weights × 0.2: std shrinks to about 0.63.
  • Weights ÷ √10: std stays at 1 (measured 1.01).
w = torch.randn(10, 200) / 10**0.5       # divide by sqrt(fan_in)
y = x @ w
y.std()                                  # 1.01

He says that mathematically, working through the variance of the product, the correct answer is to divide by the square root of the fan-in.

My note
Each output adds up 10 products, and variances of independent terms add. So the std grows by √10, and dividing the weights by √10 cancels it.
In one lineDividing the weights by √fan_in keeps the output at the same standard deviation as the input.
18

Kaiming (He) initialisation and the gain

▶ 32:00

This is studied in the paper “Delving Deep into Rectifiers” (He et al., 2015), for ReLU networks.

  • ReLU throws away half of the distribution (negatives become 0). To make up for it, the weights need an extra factor: std = √(2 / fan_in) instead of √(1 / fan_in).
  • The paper also studies the backward pass. They find that if the forward pass is well scaled, the backward pass is about as well scaled, up to a constant. So the choice does not matter much.
  • He calls this probably "the most common way of initialising neural networks now".
In one lineFor ReLU the weights get an extra factor of √2 because half the signal is discarded.

In PyTorch: kaiming_normal_ and the gain

▶ 34:00
std = gain ÷ √fan_in
  • mode: 'fan_in' (default) keeps the activations normalised; 'fan_out' keeps the gradients normalised. The paper says it doesn't matter much, so most people keep the default.
  • nonlinearity: the gain depends on what comes after the layer.
nonlinearitygain
linear / identity1
ReLU√2
tanh5/3

Why a gain at all? tanh and ReLU are contractive: they squeeze the tails of the distribution in. We boost the weights a bit to fight the squeezing and renormalise back to unit std.

In one lineFor tanh the PyTorch gain is 5/3, a boost that compensates for tanh squeezing its inputs.

Why he skips the details: modern tricks

▶ 36:00

About seven years ago you had to be extremely careful with activations, gradients, their ranges, histograms, precise gains. Everything was "finicky and fragile", especially for deep nets.

Modern innovations make exact initialisation much less important:

  1. Residual connections (covered later).
  2. Normalisation layers: batch norm, layer norm, group norm.
  3. Better optimisers: not plain SGD, but RMSProp and especially Adam.

What he does in practice: divide the weights by √fan_in, roughly what we just did.

In one lineResidual connections, normalisation layers and Adam make exact initialisation far less critical today.

In practice: std = gain / √fan_in

▶ 37:00

torch.randn has std 1, so multiplying by a number sets the std to that number.

(torch.randn(10000) * 0.2).std()                    # 0.2010

fan_in = n_embd * block_size                        # 10 * 3 = 30
W1 = torch.randn((fan_in, n_hidden), generator=g) * (5/3) / fan_in**0.5
b1 = torch.randn(n_hidden, generator=g) * 0.01
W2 = torch.randn((n_hidden, vocab_size), generator=g) * 0.01
b2 = torch.randn(vocab_size, generator=g) * 0
  • He first used 10 as the fan-in, then noticed it is 30: each character has 10 numbers and we glue three together.
  • So the std becomes (5/3) ÷ √30 ≈ 0.30, against the 0.2 we found by eye.
  • Training again, validation loss lands at about 2.10, "the same spot", but with no magic numbers from guessing.
In his words
This is “semi-principled” and will scale to much bigger networks, something we can use as a guide.
In one lineWeights get std = gain / √fan_in; for tanh and fan-in 30 that is 0.30, and the loss stays at 2.10.

Part 4 · 40:30 – 1:18:00

Batch normalisation

Stop hoping the activations stay Gaussian: force them to be.

22

The big idea of batch norm

▶ 40:30

Batch normalisation came out in 2015 from a team at Google. It made it possible to train very deep networks reliably: "it basically just worked".

  • We want the pre-activations roughly Gaussian (mean 0, std 1), at least at the start. Not too small (the tanh does nothing), not too large (the tanh saturates).
  • The insight: why not just normalise them to be Gaussian? It sounds crazy, but standardising is a perfectly differentiable operation, so backprop works through it.
  • He says his mind was blown when he first read it.
In one lineBatch norm simply standardises the pre-activations, and because that is differentiable, you can train through it.
23

Standardise over the batch

▶ 42:00
hpreact = embcat @ W1 + b1                           # (32, 200)
hpreact = (hpreact - hpreact.mean(0, keepdim=True)) / hpreact.std(0, keepdim=True)
  • hpreact is 32 examples × 200 neurons. We take the mean down dimension 0 (over the batch) and keep the shape: (1, 200). Same for the std.
  • Subtract the mean, divide by the std. Now every neuron has exactly mean 0 and std 1 over these 32 examples.
  • That is why it is called batch normalisation: we normalise using the batch.
x̂ = (x − μbatch) ÷ √(σ2batch + ε)

The paper's version adds a tiny ε under the square root. More on that later.

In one lineSubtract each neuron's batch mean and divide by its batch std: every neuron becomes unit Gaussian.
24

But don't force it forever: scale and shift

▶ 45:30

We want Gaussian at initialisation, not forced for ever. The net should be able to make some neurons more spread out, sharper, more or less "trigger happy". So the paper adds a scale and shift:

bngain = torch.ones((1, n_hidden))          # gamma, starts at 1
bnbias = torch.zeros((1, n_hidden))         # beta,  starts at 0
parameters = [C, W1, b1, W2, b2, bngain, bnbias]    # trained by backprop

hpreact = embcat @ W1 + b1
hpreact = bngain * (hpreact - hpreact.mean(0, keepdim=True)) / hpreact.std(0, keepdim=True) + bnbias
  • At the start γ = 1 and β = 0, so each neuron is exactly unit Gaussian.
  • During training backprop can change γ and β, so the net may reshape the distribution however it likes.
  • They must be in the parameters list. The count goes from 11,897 to 12,297 (+200 +200).
  • Do the same normalise-and-scale at test time too.
In one lineγ and β start at 1 and 0 and are learned, so the net can undo or reshape the normalisation as it needs.
25

The result, and when batch norm matters

▶ 48:00

Validation loss comes out at about 2.10 (screen: train 2.0668, val 2.1048). Not better, and he did not expect it to be.

  • We have one hidden layer, and there we could work out the right weight scale ourselves. Batch norm has nothing left to fix.
  • In a deep net with many kinds of layers and residual connections, tuning every weight scale by hand quickly becomes intractable.
  • Instead you sprinkle batch norm layers throughout. The usual place: right after each linear or convolutional layer, to control the scale of its output.
  • It does not need perfect mathematics for every kind of building block, and it stabilises training, which is why it is popular.
In one lineOn this tiny net batch norm changes nothing (val 2.10), but in deep nets it replaces fragile hand-tuning.
26

The catch: examples become coupled

▶ 50:30

The stability has "a terrible cost". Something strange and unnatural happens.

  • Before: each example went through the net alone. Batches were just an efficiency trick.
  • Now the mean and std come from the whole batch, so an example's hidden state and logits depend on which other examples were drawn with it. They "jitter" from batch to batch.
  • You would think that is a bug. But oddly it helps: the jitter is a regulariser. It pads out each example with a little noise, a bit like data augmentation, so the net finds it harder to overfit.
  • That side effect is a reason batch norm is hard to remove.
  • But "no one likes this property": it causes many bugs. People have tried to replace it with layer norm, instance norm, group norm, which don't couple examples. Batch norm "just works quite well", so it stays.
In one lineBatch norm makes each example depend on its batch mates; the noise regularises, but it also causes bugs.
27

At test time: one example, no batch

▶ 54:30

When we deploy, we want to feed one example. But the net now expects a batch to compute a mean and std. How?

The paper's first answer: after training, compute the mean and std once over the whole training set and fix them.

with torch.no_grad():
    emb = C[Xtr]
    embcat = emb.view(emb.shape[0], -1)
    hpreact = embcat @ W1 + b1
    bnmean = hpreact.mean(0, keepdim=True)
    bnstd  = hpreact.std(0, keepdim=True)

# at evaluation time, use the fixed numbers
hpreact = bngain * (hpreact - bnmean) / bnstd + bnbias
  • The loss is basically identical (train 2.0668, val 2.1049).
  • And now a single example can be forwarded, because mean and std are fixed numbers.
In one lineAfter training, compute the mean and std once over the training set and use them at inference.
28

Running statistics, in one stage

▶ 56:30

"Nobody wants a second stage after training, because everyone is lazy." The paper's other idea: keep a running mean and std while training.

bnmean_running = torch.zeros((1, n_hidden))      # start: mean 0
bnstd_running  = torch.ones((1, n_hidden))       # start: std 1

# inside the training loop, after computing this batch's bnmeani and bnstdi
with torch.no_grad():
    bnmean_running = 0.999 * bnmean_running + 0.001 * bnmeani
    bnstd_running  = 0.999 * bnstd_running  + 0.001 * bnstdi
  • Starting values: at init hpreact is about unit Gaussian, so mean 0 and std 1 are good guesses.
  • These are not parameters: no gradient is ever taken for them, so the update sits under no_grad. It is a "janky" smooth running average.
  • After training the running numbers are very similar to the ones computed in one pass over the training set, "not identical but pretty close". The validation loss is basically the same.
  • So we can drop the second stage. PyTorch's batch norm layer works exactly like this.
In one lineUpdate a running mean and std during training (0.999 old + 0.001 new), so no second calibration stage is needed.

Two small details: epsilon and the useless bias

▶ 61:00

1. Epsilon. The formula divides by √(variance + ε), with ε a small number, by default 1e-5. It prevents a division by zero if a batch's variance is exactly zero. He leaves it out here because it is unlikely in this example.

2. The bias before batch norm is wasted.

hpreact = embcat @ W1 + b1          # b1 is added...
hpreact = bngain * (hpreact - mean) / std + bnbias    # ...then subtracted out by the mean
  • Whatever bias you add, the batch mean subtracts it again. So b1.grad is zero: it never learns.
  • With batch norm after a weight layer, leave the bias out (bias=False). The batch norm layer has its own bias, β, which takes over that job.
  • With b1 removed the parameter count falls to 12,097 (screen).
  • Keeping it is not catastrophic, just wasteful.

A batch norm layer, summarised

▶ 63:00
  • It controls the statistics of the activations in the net. Sprinkle it throughout, usually after layers with multiplications (linear, convolution).
  • Parameters: the gain γ and bias β, trained with backprop.
  • Buffers: the running mean and running std, updated by the moving average, not by gradients.
  • What it does: compute the mean and std of the batch, centre and scale it to unit Gaussian, then scale and offset by the learned γ and β. Meanwhile it keeps the running statistics.
  • At inference it uses the running numbers, so a single example can be forwarded.
In one lineA batch norm layer normalises with batch statistics in training and with running statistics at inference.

PyTorch's Linear and BatchNorm1d

▶ 69:00

nn.Linear computes x @ W + b.

  • It needs in_features (fan-in) and out_features (fan-out), and a bias flag. Set bias=False if a normalisation layer follows.
  • Default initialisation: uniform between −√k and +√k, with k = 1/fan_in. So the scale is 1/√fan_in, the same idea as ours but without a gain and drawn uniformly instead of from a Gaussian.

nn.BatchNorm1d(num_features) is the layer we built. Its main options:

optionmeaning

What are the steps of a batch norm layer?
Compute the batch mean and std per neuron, standardise to mean 0 and std 1, then multiply by a learnable gain γ and add a learnable bias β.
Why do we need γ and β?
We want unit Gaussian only at initialisation. γ and β let the net move, widen or sharpen the distribution as training needs.
What strange property does batch norm introduce, and what good and bad does it do?
Examples in a batch become coupled, since their statistics depend on each other. It acts as a regulariser (jitter, like augmentation) but causes bugs.
How do you run the net on a single example after training?
Use fixed statistics: either calibrate them once over the training set, or use the running mean and std tracked during training.
What is the difference between the parameters and the buffers of the layer?
Parameters (γ, β) are trained by backprop. Buffers (running mean and std) are updated by a moving average and get no gradients.
Why drop the bias in the Linear layer before a batch norm?
The batch mean subtraction cancels it, so its gradient is zero. The β of the batch norm does that job.
What does epsilon do?
It is added to the variance so the division can't be by zero.
Why might momentum 0.1 be risky for a batch of 32?
Small batches give noisy mean and std estimates, so a fast running average can thrash instead of settling.

His own summary of the lecture so far:

  • Look at the activations and gradients, especially as nets get bigger and deeper.
  • At the output layer, over-confident mistakes create hockey-stick losses. Fix it and training does less wasteful work.
  • Keep activations from squashing to zero or exploding. You want them fairly homogeneous: roughly Gaussian everywhere.

Layers as classes: Linear

▶ 79:30

Now the code is arranged like PyTorch: small modules that you can stack like Lego bricks.

class Linear:
    def __init__(self, fan_in, fan_out, bias=True):
        self.weight = torch.randn((fan_in, fan_out), generator=g) / fan_in**0.5
        self.bias = torch.zeros(fan_out) if bias else None

    def __call__(self, x):
        self.out = x @ self.weight
        if self.bias is not None:
            self.out += self.bias
        return self.out

    def parameters(self):
        return [self.weight] + ([] if self.bias is None else [self.bias])
  • The same inputs as nn.Linear: fan-in, fan-out, and whether to have a bias.
  • The weight is a Gaussian divided by √fan_in; the bias starts at zero.
  • Calling the layer computes x @ W (+ b). parameters() returns its tensors.
In one lineLinear stores a weight scaled by 1/√fan_in and a zero bias, and applies x @ W + b when called.

Layers as classes: BatchNorm1d

▶ 81:00
class BatchNorm1d:
    def __init__(self, dim, eps=1e-5, momentum=0.1):
        self.eps = eps
        self.momentum = momentum
        self.training = True
        # parameters (trained with backprop)
        self.gamma = torch.ones(dim)
        self.beta = torch.zeros(dim)
        # buffers (trained with a running 'momentum update')
        self.running_mean = torch.zeros(dim)
        self.running_var = torch.ones(dim)

    def __call__(self, x):
        if self.training:
            xmean = x.mean(0, keepdim=True)          # batch mean
            xvar = x.var(0, keepdim=True)            # batch variance
        else:
            xmean = self.running_mean
            xvar = self.running_var
        xhat = (x - xmean) / torch.sqrt(xvar + self.eps)
        self.out = self.gamma * xhat + self.beta
        if self.training:
            with torch.no_grad():
                self.running_mean = (1 - self.momentum) * self.running_mean + self.momentum * xmean
                self.running_var  = (1 - self.momentum) * self.running_var  + self.momentum * xvar
        return self.out

    def parameters(self):
        return [self.gamma, self.beta]
  • self.training: PyTorch modules have this flag because behaviour differs. In training use the batch statistics and update the running ones. In evaluation use the running ones and don't update.
  • Only gamma and beta are returned by parameters(). The running values are buffers.
  • He now tracks the variance, as in the paper, instead of the std. They are very similar.
  • self.out is not in real PyTorch. He keeps it so he can plot every layer's output later.
  • torch.no_grad() stops PyTorch building a graph for the buffer updates, since we never call backward on them.
In one lineBatchNorm1d keeps γ and β as parameters and the running mean and variance as buffers, switching on a training flag.

Why a gain of 5/3?

▶ 88:30
  • Gain 1 (no boost): the std shrinks layer by layer towards zero, and saturation goes to zero too. The first layer is fine, the later ones fade.
  • Why: a stack of linear layers with 1/√fan_in preserves std, but the tanh layers squash the distribution, so some gain is needed to keep expanding it.
  • Gain 3: saturations become way too large.
  • 5/3 is a good setting for a sandwich of Linear and tanh.

What if there is no tanh at all?

▶ 92:30

Remove every tanh but keep the gain at 5/3: a giant linear sandwich.

  • The correct gain here is exactly 1, the std-preserving one. 5/3 is too high.
  • With 5/3: the activations start tight and become very diffuse by layer 4. The gradients go the other way and diminish in the deeper layers: an asymmetry. Imagine this with 50 layers.
  • Too large a gain does this, too small does the opposite. Before batch norm this was "incredibly tricky" to set.

So why have tanh at all? A stack of linear layers collapses into one linear layer: all the Wx + b merge into a single Wx + b. The forward function is just linear, however many layers there are.

  • Interestingly the training dynamics still differ, because the chain rule behaves differently. There are papers on infinitely deep linear networks.
  • The tanh is what turns the sandwich into a network that can, in principle, approximate any function.
In one lineWithout nonlinearities the right gain is 1, and the layers would collapse into a single linear function anyway.

Plot 4: update-to-data ratio over time

▶ 100:00

What really matters is not the gradient-to-data ratio but the update-to-data ratio: how much the values actually change on each step.

Batch norm makes the gain forgiving

▶ 109:30

What we gain: much less brittleness about the weight scale.

  • Change the gain of the linear layers (for example to 0.2). The activations are completely unaffected, because of the explicit normalisation. Gradients and weight gradients still look okay.
  • But the update ratios change. The scale of the incoming activations interacts with the batch norm's backward pass, so the effective step size moves. So you may need to retune the learning rate.
  • With bigger gains the updates come out lower; so there is still no completely free pass on the weights.
  • Remove the fan-in scaling too (plain random weights, no gain): the forward and backward statistics still look fine, with slightly fat tails on a few layers.
  • But the update ratios are well below −3, by about a factor of ten. The fix: raise the learning rate about 10× (from 0.1 to 1.0), and then everything is in range again.
In one lineBatch norm makes activations robust to the weight scale, but you may have to retune the learning rate.

Gotchas he points out

▶ 50:30
  1. A starting loss far above −ln(1/vocab) means a confidently wrong net. Fix the last layer's scale.
  2. Don't set weights exactly to zero. Use small random values.
  3. Saturated tanh, dead ReLU: flat regions give zero gradient. Look for a fully white column.
  4. Use fan-in 30, not 10, when 3 characters × 10 numbers feed the layer.
  5. The bias before a batch norm is useless. Use bias=False.
  6. Batch norm couples the examples in a batch. It causes bugs; prefer layer or group norm when you can.
  7. Single-example inference needs fixed statistics: running mean and std.
  8. The running averages are buffers, not parameters. Update them under no_grad.
  9. Momentum 0.1 may be too fast for tiny batches (like 32).
  10. With batch norm, a different weight scale means a different effective learning rate. Re-check the update ratio.
  11. Look at the plots over time, not one frozen step.
